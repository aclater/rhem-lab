Guided exercise 10 os-update

Update and roll back the operating system

Update the operating system of the whole fleet, one device first and the rest only if that one succeeds. Then go back to the previous version.

Outcomes

  • A second OS release, edge-os:v2, in your registry.
  • All three devices updated to it in two stages, without logging in to any of them.
  • The fleet returned to v1, to see what going back looks like.

Note

How an image mode update works. The device downloads the new OS image next to the running one, marks it for the next boot, and reboots. The previous image stays on disk. So an OS update is one reboot long, the same on every device, and reversible. Applications are pulled again only if their images changed.

Before you begin

On the workstation, in ~/edgelab, confirm that the earlier exercises are complete:

./lab start os-update

Instructions

Build OS release v2

Make a small visible change to the OS: a file that says which release this is. Edit the Containerfile:

cd ~/device
vi Containerfile

Add this line just above the last line of the file, RUN bootc container lint, then save and quit:

RUN echo "edge-os v2" > /etc/edge-os-version

Confirm the change, then build and push the image under the new tag:

tail -3 Containerfile
sudo podman build -t rhem.lab.internal:8443/admin/edge-os:v2 .
sudo podman push rhem.lab.internal:8443/admin/edge-os:v2

RUN echo "edge-os v2" > /etc/edge-os-version

RUN bootc container lint
  • In practice this step is where security fixes arrive: rebuilding from the current RHEL base image picks up the latest packages.
  • No new disk image is needed. Disk images are only for installing new devices; existing devices take the OS image from the registry.
  • v1 stays in the registry untouched. You need it to go back.

Change the fleet: new OS, one device first

cat > ~/fleet/lab-fleet.yaml <<'EOF'
apiVersion: flightctl.io/v1beta1
kind: Fleet
metadata:
  name: lab
spec:
  selector:
    matchLabels:
      site: lab
  rolloutPolicy:
    deviceSelection:
      strategy: BatchSequence
      sequence:
        - selector:
            matchLabels:
              alias: edge-1
          limit: 1
    successThreshold: 100%
  template:
    spec:
      os:
        image: rhem.lab.internal:8443/admin/edge-os:v2
      applications:
        - name: hello
          appType: container
          image: rhem.lab.internal:8443/admin/hello:v2
          runAs: flightctl
          ports:
            - "8080:8080"
EOF
flightctl apply -f ~/fleet/lab-fleet.yaml

Two things changed: os.image is now v2, and there is a rolloutPolicy.

FieldMeaning
sequenceThe batches, in order. Here one batch: at most one device (limit: 1) from those labelled alias: edge-1.
(implicit last batch)Every device not picked by an earlier batch. You do not write it down.
successThreshold: 100%The share of a batch that must update successfully before the next batch starts. With one device in the batch: it must succeed.

Note

Why stage a rollout? An OS update that fails to boot on one device will fail on all identical devices. Updating one first limits the damage to one. In a large fleet you would use label selectors and percentages instead of a single name: one device per site, then 10%, then the rest.

The device now boots v2 and holds v1 as its rollback image. Nothing has to be downloaded to go back.

Go back to v1

Going back is not a special operation. You tell the fleet the devices should run v1, and they make it so:

vi ~/fleet/lab-fleet.yaml

Change the os image tag from v2 back to v1, save and quit. Then confirm the change, apply it and watch:

grep image: ~/fleet/lab-fleet.yaml
flightctl apply -f ~/fleet/lab-fleet.yaml
watch -n 5 flightctl get devices

Each device reboots into the image it already holds, so nothing is downloaded and this is quicker than the update. In test runs it took between two and a half and six minutes for all three devices to be back on v1 and serving the application again (a device shows Updating and NoApplications until then). The shortest run changed all devices at once. Your fleet file still has the rollout policy, so edge-1 goes first again and the others follow, which takes longer.

ssh -F ~/edgelab/ssh_config edge-1 sudo bootc status

● Booted image: containers-storage:rhem.lab.internal:8443/admin/edge-os:v1
...output omitted...
  Rollback image: containers-storage:rhem.lab.internal:8443/admin/edge-os:v2
...output omitted...

The two images have swapped places: v1 is booted, and v2 is now the one kept in reserve.

Note

Two kinds of going back. What you just did is a decision made at the server: the fleet says v1. Image mode also supports an automatic kind on the device, where health checks run after an update (greenboot) and a failing image is replaced by the previous one at the next boot. Edge Manager ships a flightctl-greenboot package for that. This lab does not install it or break an image on purpose; the rollback image you saw above is what that mechanism would use.

Evaluation

On the workstation, in ~/edgelab, grade your work. Every line should end in SUCCESS; a FAIL line is followed by what to do about it.

./lab grade os-update

You can also check by hand:

flightctl get devices

All three devices are UpToDate and Healthy, on the OS release the fleet names.

What you have built

A complete loop: an OS image and an application image in a registry you run, a fleet file that names exact versions of both, and devices that converge on that file by themselves, in stages, with a way back. Every change to the edge was a change to lab-fleet.yaml.
