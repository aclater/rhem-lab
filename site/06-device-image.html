Guided exercise 6 image-build

Build the device image

Build the operating system your edge devices will run: RHEL in image mode, with the Edge Manager agent and everything the agent needs to find and trust your server. Then turn it into a disk a VM can boot.

Outcomes

  • An OS image rhem.lab.internal:8443/admin/edge-os:v1 in your registry.
  • A bootable disk image made from it, copied to the workstation as ~/edgelab/images/edge-os-v1.qcow2.

Note

This is Red Hat Device Edge. The device OS is RHEL built as a container image (image mode, the tool is bootc). You describe the whole operating system in a Containerfile, build it like an application image, and devices boot it directly. An update is a new image; the device downloads it, reboots into it, and keeps the previous one to fall back to. Nothing is ever patched in place, so every device running edge-os:v1 is identical.

Before you begin

On the workstation, in ~/edgelab, confirm that the earlier exercises are complete:

./lab start image-build

Instructions

Request an enrollment certificate

A new device has to prove it is allowed to ask for enrollment. That proof is a certificate, which you request from the server and put into the image.

mkdir ~/device
cd ~/device
flightctl certificate request --signer=enrollment --expiration=365d --output=embedded > config.yaml
chmod 600 config.yaml
grep -v data: config.yaml

enrollment-service:
  authentication:
  enrollment-ui-endpoint: https://rhem.lab.internal
  service:
    server: https://rhem.lab.internal:7443/
...output omitted...

The file also holds three long lines ending in -data: followed by encoded certificates and a key. grep -v data: leaves those lines out so that you can read the rest.

This file is the agent's whole configuration. Three things in it shape everything a device does:

FieldMeaningConsequence
serverWhere the agent connects: your base domain, port 7443.The device finds the server by name. Whatever answers to that name with the right certificate is "the server".
certificate-authority-dataEdge Manager's CA certificate.The device talks only to a server whose certificate this CA signed.
client-certificate-data, client-key-dataThe enrollment certificate and its key, valid 365 days.Lets a device ask to enroll. It grants nothing else: each request still needs your approval.

Note

Early binding. Putting this file in the image is called early binding: every device made from the image already knows its server. The alternative, late binding, leaves it out and injects it when a device is provisioned, so one image can serve several Edge Manager installations. All devices share this enrollment certificate; each one creates its own private key on first boot and gets its own identity certificate when you approve it.

Warning

The file contains a private key. Anyone holding it can submit enrollment requests to your server until it expires. That is why the image goes in your own registry, and why approval is a deliberate step.

Collect the registry's CA

Devices will pull their OS updates and applications from your registry, so they have to trust its certificate authority.

sudo cat /opt/quay/quay-rootCA/rootCA.pem > registry-ca.pem
openssl x509 -in registry-ca.pem -noout -subject

Write the Containerfile

cat > Containerfile <<'EOF'
FROM registry.redhat.io/rhel9/rhel-bootc:9.8

# The Edge Manager agent, from the same repository stream as the server.
RUN dnf config-manager --set-enabled edge-manager-1.4-for-rhel-9-x86_64-rpms && \
    dnf -y install flightctl-agent && \
    dnf -y clean all && \
    systemctl enable flightctl-agent.service

# Where the server is, which CA to trust for it, and the certificate that lets a new device ask to enroll.
ADD config.yaml /etc/flightctl/config.yaml

# Trust the lab registry, so the device can pull OS updates and applications from it.
ADD registry-ca.pem /etc/pki/ca-trust/source/anchors/lab-registry-ca.pem
RUN update-ca-trust

# Lab convenience: members of wheel may use sudo without a password.
RUN echo "%wheel ALL=(ALL) NOPASSWD: ALL" > /etc/sudoers.d/wheel-nopasswd

RUN bootc container lint
EOF
LineWhat it doesEffect on the device
FROM …/rhel9/rhel-bootc:9.8Red Hat's bootable RHEL 9.8 base image: a kernel, systemd, podman and the image-mode tooling.The device runs the same RHEL release as the server.
dnf config-manager …, dnf install flightctl-agentEnables the Edge Manager repository inside the build and installs the agent, version 1.4.0 to match the server.Also creates a flightctl system user, which applications run as, and turns off image mode's own automatic updates so that Edge Manager alone decides when the OS changes.
systemctl enable flightctl-agent.serviceStarts the agent at boot.A device enrolls by itself the first time it is powered on.
ADD config.yamlThe file from step 1.Early binding.
ADD registry-ca.pem, update-ca-trustAdds your registry's CA to the system trust store.Without it, every image pull on the device fails with a certificate error.
bootc container lintChecks the result for mistakes that would stop it booting.Problems fail the build here, not on a device in the field.

Important

Differs from the 1.3 documentation. Red Hat's 1.3 procedure adds useradd … flightctl to this step. With the 1.4 agent package that line fails the build ("user 'flightctl' already exists"), because the package now creates the user itself.

Build and push the OS image

sudo podman build -t rhem.lab.internal:8443/admin/edge-os:v1 .
sudo podman push rhem.lab.internal:8443/admin/edge-os:v1
sudo podman images rhem.lab.internal:8443/admin/edge-os

About two minutes. The image is around 2 GB.

  • It builds here because this VM is registered. Podman on a registered RHEL host passes the host's entitlement into the build, which is what lets dnf inside the image reach the RHEL and Edge Manager repositories. On an unregistered machine the first RUN fails.
  • sudo matters: the next step reads the image from root's image store.
  • The name is registry/account/repository:tag. admin is the registry account from module 5. The tag v1 is how you will tell OS releases apart.

Look inside the image without booting it:

sudo podman run --rm rhem.lab.internal:8443/admin/edge-os:v1 \
  sh -c "rpm -q flightctl-agent; id flightctl; systemctl is-enabled flightctl-agent; ls -l /etc/flightctl/"

flightctl-agent-1.4.0-1.el9.x86_64
uid=1000(flightctl) gid=1000(flightctl) groups=1000(flightctl)
enabled
total 8
-rw-------. 1 root root 4135 … config.yaml

Turn the image into a disk

A registry image cannot be booted by a new machine with an empty disk. bootc-image-builder converts it into a disk image; here a qcow2 for KVM. A small settings file adds a login user, lab, with your lab public key.

First copy the public key from the workstation to the server VM:

scp -F ~/edgelab/ssh_config keys/id_ed25519.pub rhem:device/lab-key.pub

Then, in the server VM, write the settings file. The word LAB_PUBLIC_KEY is a marker; enter it as shown:

cd ~/device
cat > config.toml <<'EOF'
[[customizations.user]]
name = "lab"
groups = ["wheel"]
key = "LAB_PUBLIC_KEY"
EOF

Now replace the marker with the key. Enter this command exactly as shown; do not substitute anything yourself. sed swaps the marker word for the content of the key file you just copied, which the part in $( ) reads:

sed -i "s|LAB_PUBLIC_KEY|$(cat lab-key.pub)|" config.toml
cat config.toml
mkdir output

[[customizations.user]]
name = "lab"
groups = ["wheel"]
key = "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA… edgelab"

The key line must now hold the key itself, starting with ssh-ed25519. If it still says LAB_PUBLIC_KEY, the devices will boot but you will not be able to log in to them.

Build the disk:

sudo podman run --rm --privileged --pull=newer \
  --security-opt label=type:unconfined_t \
  -v ./config.toml:/config.toml:ro \
  -v ./output:/output \
  -v /var/lib/containers/storage:/var/lib/containers/storage \
  registry.redhat.io/rhel9/bootc-image-builder:latest \
  --type qcow2 \
  rhem.lab.internal:8443/admin/edge-os:v1
sudo ls -lh output/qcow2/

-rw-r--r--. 1 root root 1.4G … disk.qcow2

About three minutes. What the options do:

OptionWhy
--privileged, --security-opt …The builder partitions a disk file and installs a boot loader into it, which needs device access a normal container does not have.
-v /var/lib/containers/storage:…Lets the builder read the OS image from root's local image store instead of pulling it again.
--type qcow2The disk format. Others include iso (an installer for bare metal), raw and vmdk.
config.tomlDisk-time customization. The user lab exists only on machines installed from this disk; it is not part of the OS image.

Note

Image versus disk. The disk image is only used once per device, to get it started. From then on the device follows the OS image in the registry: the disk records that it came from rhem.lab.internal:8443/admin/edge-os:v1, and updates arrive as new tags of that image. For real hardware you would build an iso or raw image from the same OS image; nothing else changes.

Copy the disk to the workstation

scp -F ~/edgelab/ssh_config rhem:device/output/qcow2/disk.qcow2 images/edge-os-v1.qcow2
qemu-img info images/edge-os-v1.qcow2

image: images/edge-os-v1.qcow2

This is the master copy. Each edge VM gets its own copy of it in the next module.

Evaluation

On the workstation, in ~/edgelab, grade your work. Every line should end in SUCCESS; a FAIL line is followed by what to do about it.

./lab grade image-build

You can also check by hand:

sudo podman search --list-tags rhem.lab.internal:8443/admin/edge-os

NAME                                   TAG
rhem.lab.internal:8443/admin/edge-os   v1

The image is in the registry, and the disk made from it is on the workstation.

Finish

./lab finish image-build

This confirms that the exercise is complete and names the next one. Nothing is cleaned up, because the later exercises build on what you made here.
