Guided exercise 4 rhem-login

Log in for the first time

A fresh Edge Manager has no users. Create an administrator, make the server VM trust the lab CA, and log in with the CLI and the web UI.

Outcomes

  • A user admin with the administrator role.
  • flightctl logged in on the rhem VM.
  • The web UI open in your browser at https://rhem.lab.internal.

Before you begin

On the workstation, in ~/edgelab, confirm that the earlier exercises are complete:

./lab start rhem-login

Instructions

Create an administrator

The bundled login provider checks usernames and passwords against ordinary Linux accounts, but inside its own container, not on the VM. A user's role comes from the groups they are in.

Create the administrators' group:

sudo podman exec flightctl-pam-issuer groupadd -f flightctl-admin

Create the user admin in that group:

sudo podman exec flightctl-pam-issuer useradd -m --groups flightctl-admin admin

The user has no password yet and cannot log in. Set the lab password, edgelab123:

echo "admin:edgelab123" | sudo podman exec -i flightctl-pam-issuer chpasswd

chpasswd reads a line of the form user:password and sets that user's password. It prints nothing when it succeeds.

Important

Lab password. This lab uses one password, edgelab123, for the two accounts it creates: this one and the registry's in the next module. A fixed, visible password is fine for a lab that only exists on your workstation. Never do this on a system that others can reach.

Confirm that the user exists:

sudo podman exec flightctl-pam-issuer id admin

uid=1000(admin) gid=1001(admin) groups=1001(admin),1000(flightctl-admin)
GroupRole (from the product documentation; only flightctl-admin is used in this lab)
flightctl-adminEverything, including approving devices and managing other resources.
flightctl-operatorDay-to-day device and fleet management.
flightctl-viewerRead-only.

Note

Where the accounts live. In the podman volume flightctl-pam-issuer-etc, so they survive restarts and upgrades. For a real deployment you would point Edge Manager at your organization's identity provider instead (auth in service-config.yaml); the bundled provider keeps the lab self-contained.

Trust the lab CA on the server VM

The server's certificate is signed by the CA it created for itself, which nothing trusts yet. Add that CA to the VM's system trust store:

sudo install -m 0644 /etc/flightctl/pki/ca.crt /etc/pki/ca-trust/source/anchors/rhem-lab-ca.crt
sudo update-ca-trust
curl -I https://rhem.lab.internal/

HTTP/1.1 200 OK
...output omitted...

curl now succeeds without --cacert. So will flightctl and podman.

Note

Why not just skip verification? flightctl login has an --insecure-skip-tls-verify flag, and it would work. But trusting one CA is the habit you need at the edge: devices will be given exactly this CA so that they talk to your server and nothing else.

Log in with the CLI

flightctl login https://rhem.lab.internal --username admin --password edgelab123
flightctl version

Auto-selected organization: 00000000-0000-0000-0000-000000000000 Default
Login successful.
Client Version: v1.4.0
Server Version: v1.4.0
  • The login is stored in ~/.config/flightctl/client.yaml as a token. When it expires, log in again.
  • Everything you create belongs to an organization. A standalone install has one, Default.
  • If the two versions differ, install the matching flightctl-cli.

Look around with the CLI

flightctl get organizations
flightctl get devices
flightctl get enrollmentrequests
flightctl get fleets

All empty apart from the organization. These three kinds are the core of everything that follows:

KindWhat it isModule
EnrollmentRequestA new device asking to be let in. Waits for your approval.7
DeviceAn approved device: its desired spec and its reported status.7
FleetA spec template applied to all devices with matching labels.8

flightctl --help lists the commands. They follow the kubectl pattern: get, apply -f, edit, delete, with resources written as YAML.

Open the web UI

Your browser runs on the workstation, which does not know the name rhem.lab.internal yet. Tell the workstation's resolver to ask the lab network's DNS for that one domain:

sudo resolvectl dns virbr-rhem 192.168.160.1
sudo resolvectl domain virbr-rhem '~lab.internal'
resolvectl query rhem.lab.internal

rhem.lab.internal: 192.168.160.10                    -- link: virbr-rhem
  • The ~ means "use this DNS server only for names under lab.internal". Everything else keeps using your normal DNS.
  • Nothing is written to disk. The setting disappears when the lab network is stopped or the workstation reboots; run the two commands again after that.

Then open https://rhem.lab.internal. The browser warns about the certificate, because it does not know the lab CA. Accept the warning for this site, and log in as admin with the password edgelab123.

Important

The name is required. The web UI does not work by IP address, because its login page redirects to https://rhem.lab.internal/….

In the UI, find Devices, Fleets and Repositories in the left menu. It shows the same objects as the CLI; the guide uses the CLI because commands can be repeated and kept in git, and suggests when to look at the UI.

Evaluation

On the workstation, in ~/edgelab, grade your work. Every line should end in SUCCESS; a FAIL line is followed by what to do about it.

./lab grade rhem-login

You can also check by hand:

flightctl version && flightctl get devices

Both versions print as v1.4.0 and the device list is empty, without any certificate or login error.

Where you are

The management side is complete: a server with its own CA, a database, and an administrator. Next come the things it manages. Devices need two things before they can exist: a registry to pull images from (module 5) and an operating system image that knows how to find this server (module 6).

Finish

./lab finish rhem-login

This confirms that the exercise is complete and names the next one. Nothing is cleaned up, because the later exercises build on what you made here.
