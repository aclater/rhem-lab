Appendix C iso-install

Install a device from an ISO

The three devices so far started from a ready-made disk. A physical device usually starts empty and is installed from boot media. Here you turn the device image into an installer ISO that needs no answers, and install a fourth device from it.

Outcomes

  • An installer ISO, built from edge-os:v1, that carries the OS image and a kickstart file: the installer's instructions.
  • A fourth device, edge-4, installed from that ISO on an empty disk with no questions asked.
  • edge-4 enrolled, in the fleet, and running what the fleet says.

How an ISO install differs from a disk image

Disk image (module 6)Installer ISO (this appendix)
What you buildA finished disk. The device boots it as it is.Boot media. The device boots the installer, which writes the OS image to the device's own disk.
Where it fitsVMs and cloud instances, or disks written at the factory.Physical devices installed on site from a USB drive, or over the network.
The login userAdded by bootc-image-builder from config.toml.Added by the installer from the kickstart file.
The disk layoutFixed when the disk image is built.Decided by the kickstart file, on the device's real disk.

Either way the device ends up running the same OS image, follows the same registry for updates, and enrolls with the same certificate. Edge Manager cannot tell the two apart.

Before you begin

You need the lab up to and including Manage devices as a fleet, with the server VM running. The later exercises can be done before or after this one. On the workstation, in ~/edgelab:

./lab status

Important

This appendix needs the connected lab. bootc-image-builder downloads the installer's own packages from Red Hat's repositories, using the server's registration. A server built with Run the lab disconnected is not registered and cannot build the ISO.

The installer needs more memory than a running device: edge-4 gets 2 GiB. On a 16 GB workstation that still fits next to the server and the three devices.

Instructions

Write the kickstart settings

In the server VM, write a second settings file for bootc-image-builder. This one holds a kickstart file. The word LAB_PUBLIC_KEY is a marker; enter it as shown:

cd ~/device
cat > config-iso.toml <<'EOF'
[customizations.installer.kickstart]
contents = """
text
lang en_US.UTF-8
keyboard us
timezone UTC
network --bootproto=dhcp --activate
zerombr
clearpart --all --initlabel
autopart --type=lvm --noswap
rootpw --lock
user --name=lab --groups=wheel --lock
sshkey --username=lab "LAB_PUBLIC_KEY"
reboot
"""
EOF
LineMeaning
text, lang, keyboard, timezoneAnswers to the questions the installer would otherwise ask on screen.
networkBring the network up with DHCP.
zerombr, clearpart --all --initlabelErase every disk in the machine and start with an empty partition table.
autopart --type=lvm --noswapLet the installer lay out the disk: boot partitions and one LVM volume, no swap.
rootpw --lockNobody can log in as root.
user, sshkeyThe login user lab, in the group wheel, with no password and your lab public key. This replaces the [[customizations.user]] block of module 6.
rebootRestart into the installed system when done.

The file does not say which operating system to install. bootc-image-builder adds that line itself: install the OS image that it packs into the ISO, and afterwards follow that image in the lab registry for updates.

Now replace the marker with the key, as in module 6. Enter this command exactly as shown; do not substitute anything yourself. The key file lab-key.pub is still there from that module:

sed -i "s|LAB_PUBLIC_KEY|$(cat lab-key.pub)|" config-iso.toml
grep sshkey config-iso.toml
mkdir output-iso

sshkey --username=lab "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA… edgelab"

The line must now hold the key itself, starting with ssh-ed25519. If it still says LAB_PUBLIC_KEY, the device will install but you will not be able to log in to it.

Build the ISO

This is the command of module 6 with three differences: the settings file, the output folder, and --type anaconda-iso. Anaconda is the name of the RHEL installer. The build takes about six minutes.

sudo podman run --rm --privileged --pull=newer \
  --security-opt label=type:unconfined_t \
  -v ./config-iso.toml:/config.toml:ro \
  -v ./output-iso:/output \
  -v /var/lib/containers/storage:/var/lib/containers/storage \
  registry.redhat.io/rhel9/bootc-image-builder:latest \
  --type anaconda-iso \
  rhem.lab.internal:8443/admin/edge-os:v1
sudo ls -lh output-iso/bootiso/

...output omitted...

The ISO is larger than the disk image because it holds two things: the installer, and the whole OS image for the installer to write.

Copy the ISO to the workstation

scp -F ~/edgelab/ssh_config rhem:device/output-iso/bootiso/install.iso images/edge-install.iso
ls -lh images/edge-install.iso

-rw-r--r--. 1 student student 2.9G … images/edge-install.iso

Warning

This ISO erases every disk of any machine that boots from it, without asking. That is what makes it useful for installing devices, and dangerous anywhere else. Keep it in the lab.

Give the new device an address

The lab network hands fixed addresses to the machines it knows. Add edge-4 to it, while it runs and in its saved definition:

virsh -c qemu:///system net-update rhem-lab add ip-dhcp-host "<host mac='52:54:00:a0:00:24' name='edge-4' ip='192.168.160.24'/>" --live --config

Updated network rhem-lab persistent config and live state

Add the device to your SSH settings as well:

cat >> ssh_config <<'EOF'
Host edge-4
  HostName 192.168.160.24
  User lab
EOF

Install the device

Create an empty 20 GiB disk, then a VM that boots from the ISO with that disk attached:

qemu-img create -f qcow2 images/edge-4.qcow2 20G
virt-install --connect qemu:///system --name edge-4 --memory 2048 --vcpus 1 \
  --cdrom images/edge-install.iso --disk images/edge-4.qcow2 --osinfo rhel9-unknown \
  --network network=rhem-lab,mac=52:54:00:a0:00:24 \
  --boot uefi --graphics none --noautoconsole --wait -1

...output omitted...
Domain is still running. Installation may be in progress.
Waiting for the installation to complete.
Domain has shutdown. Continuing.
Domain creation completed.
Restarting guest.

where:

  • --cdrom boots the VM from the ISO, in place of --import, which booted an existing disk.
  • --wait -1 keeps the command waiting until the installer has finished, and then starts the VM again from its own disk.

The command prints nothing while the installer works, and returns after about three minutes. Nobody answered a question: the kickstart file did.

Approve every request that is not approved yet, with the fleet's label. The first part of the command lists only those requests:

for request in $(flightctl get enrollmentrequests --field-selector 'status.approval.approved!=true' -o name); do flightctl approve -l site=lab er/$request; done

The label site=lab puts the device in the fleet, and the fleet takes over. Whatever it gives the other devices, edge-4 now gets too: the application, if you have done Deploy a workload, and the fleet's OS image. If the fleet pins a different OS release from the one in the ISO, the device downloads it and restarts once: in the test for this guide a device installed from a v1 ISO was running v2 and the application three and a half minutes after approval. An ISO does not have to be rebuilt for every OS release.

Evaluation

In the server VM, the fleet owns four devices, and edge-4 settles at UpToDate like the others:

flightctl get devices

Finish

Keep edge-4 for the remaining exercises if you like; a fleet change reaches it with the others. Before Remove the lab, delete it, because that exercise only knows the first three devices:

virsh -c qemu:///system destroy edge-4
virsh -c qemu:///system undefine edge-4 --nvram
