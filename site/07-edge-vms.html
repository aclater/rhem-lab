Guided exercise 7 devices-enroll

Create and enroll edge devices

Create three edge devices from the disk image, watch them ask to join, and let them in. Nothing is configured on the devices themselves: they are identical copies that introduce themselves to the server.

Outcomes

  • Three VMs, edge-1, edge-2 and edge-3, running your OS image.
  • Three enrolled devices in Edge Manager, each labelled with its name and site=lab, all Online.

Before you begin

On the workstation, in ~/edgelab, confirm that the earlier exercises are complete:

./lab start devices-enroll

Instructions

Create the three edge VMs

cp --sparse=always images/edge-os-v1.qcow2 images/edge-1.qcow2
cp --sparse=always images/edge-os-v1.qcow2 images/edge-2.qcow2
cp --sparse=always images/edge-os-v1.qcow2 images/edge-3.qcow2

Each device gets its own copy of the disk. Then create the three VMs. The commands differ only in the name, the disk and the last two digits of the MAC address:

virt-install --connect qemu:///system --name edge-1 --memory 1536 --vcpus 1 \
  --import --disk images/edge-1.qcow2 --osinfo rhel9-unknown \
  --network network=rhem-lab,mac=52:54:00:a0:00:21 \
  --boot uefi --graphics none --noautoconsole

virt-install --connect qemu:///system --name edge-2 --memory 1536 --vcpus 1 \
  --import --disk images/edge-2.qcow2 --osinfo rhel9-unknown \
  --network network=rhem-lab,mac=52:54:00:a0:00:22 \
  --boot uefi --graphics none --noautoconsole

virt-install --connect qemu:///system --name edge-3 --memory 1536 --vcpus 1 \
  --import --disk images/edge-3.qcow2 --osinfo rhel9-unknown \
  --network network=rhem-lab,mac=52:54:00:a0:00:23 \
  --boot uefi --graphics none --noautoconsole

Starting install...
Creating domain...
Domain creation completed.
  • Each device gets 1 vCPU and 1.5 GiB of RAM (--memory is in MiB). A device running the sample application uses about 0.4 GiB.
  • There is no --cloud-init this time. Everything a device needs is already in the image, so these VMs need no restart either.
  • The MAC address is what network.xml maps to a name and an address (.21, .22, .23). The device takes its hostname from the network.
  • The devices start with UEFI Secure Boot on: the RHEL boot chain in your image is signed.

Note

This is what provisioning at the edge looks like. Write the same disk image to any number of machines and power them on. No per-device setup, no one logging in. A device's identity is created on the device at first boot, as you are about to see.

Watch the enrollment requests arrive

Within about a minute of booting, each agent creates a private key, and uses the enrollment certificate from the image to send the server a request to join.

flightctl get enrollmentrequests

NAME                                                   APPROVAL   APPROVER   APPROVED LABELS
0hv9ha1dusrut6tes7js8hbdedph814lcuo1if1gvm92t5hsgc20   Pending    <none>
1jn34ajbcdc1vhliuj5s7suq3ja49g5vjdqu101am2b9jgsrtd20   Pending    <none>
jds05pk1sdau29gqto7b4meljrpg1hn3759h4keu47b7erbebcng   Pending    <none>

Your names will differ. Run the command again until all three are listed.

  • The long name is the device's identity: a fingerprint of the public key it just generated. It is not a name anyone chose, and it cannot be copied to another machine without the private key, which never leaves the device.
  • Pending means the device is known but trusted with nothing yet.

See who is asking

A request carries what the device reports about itself. Use that to decide whether it is one of yours. Display the requests in full and page through them:

flightctl get enrollmentrequests -o yaml | less

In less, enter /hostname to jump to the first device's hostname, and n for the next one; q quits. For each request you will find:

  • Under systemInfo: the hostname, the OS image it booted, the agent version, kernel, MAC and IP address, and the product name and serial number of the hardware. On real hardware, the serial number is what you would match against your asset list before approving.
  • Under labels: alias: edge-1 (or 2, or 3). The agent proposes its hostname as the device's human-readable name.

Approve the devices, with a label

Approving does two things: the server signs an identity certificate for the device, and you attach labels. Approve every waiting request, adding the label site=lab:

for request in $(flightctl get enrollmentrequests -o name); do flightctl approve -l site=lab er/$request; done
flightctl get enrollmentrequests

Enter the first line exactly as shown. It reads: for each request name that flightctl get enrollmentrequests -o name prints, run flightctl approve -l site=lab on it. To approve a single device instead, the command is flightctl approve -l site=lab er/ followed by that request's name.

LabelWhere it came fromPurpose
alias=edge-1The agent proposed it, from the hostname. Approving kept it.A human-readable name. Edge Manager shows it in the ALIAS column and in the UI, in place of the long identity.
site=labYou added it.A property you invented. In the next module a fleet selects every device with this label. Labels like site, region, hardware type or role are how you organize thousands of devices without naming any of them.

Note

The trust chain so far. The enrollment certificate in the image let the device ask. Your approval made the server's CA sign the device's own key. From now on the device connects with that personal certificate, on port 7443, and the server knows exactly which device is talking. Approval is also available in the web UI, under Devices, where pending devices appear with an approve button.

Labels also work as filters, and -o wide shows the labels the agent added by itself (OS version, architecture, whether the device has a GPU or KVM):

flightctl get devices -l alias=edge-1
flightctl get devices -o wide

Look at a device from both sides

From the server, open a remote console to a device. This goes through the connection the device opened to the server, so it works even where you cannot reach the device directly:

flightctl console device/$(flightctl get devices -l alias=edge-1 -o name) -- hostname

Enter it exactly as shown. The part in $( ) looks up the long name of the device labelled edge-1, so you never have to copy that name by hand. The guide uses the same lookup wherever a command needs one device.

edge-1

Leave off -- hostname to get an interactive shell on the device (exit to leave).

In the lab you can also log in directly from the workstation, with the lab user that bootc-image-builder added. The first command opens a shell on the device; the second block is typed there:

ssh -F ~/edgelab/ssh_config edge-1

sudo bootc status
systemctl is-active flightctl-agent
sudo journalctl -u flightctl-agent --no-pager | grep reconciliation

● Booted image: containers-storage:rhem.lab.internal:8443/admin/edge-os:v1
        Digest: sha256:… (amd64)
       Version: 9.8 (…)
active
… msg="Spec reconciliation complete: current version 1"
  • bootc status shows that the running OS is the image edge-os:v1 from your registry.
  • Each "Spec reconciliation complete" line in the agent log is one turn of the loop that runs for the life of the device: receive a new version of the spec, make the device match it, report back.

Evaluation

On the workstation, in ~/edgelab, grade your work. Every line should end in SUCCESS; a FAIL line is followed by what to do about it.

./lab grade devices-enroll

You can also look yourself:

flightctl get devices

Three devices are listed, each with its alias, and Online in the SYSTEM column.

Where you are

Three devices are enrolled and reporting, each with its own certificate. They run the OS you built, but nothing tells them what they should run: their spec is empty. The next module gives them an owner.

Finish

./lab finish devices-enroll

This confirms that the exercise is complete and names the next one. Nothing is cleaned up, because the later exercises build on what you made here.
