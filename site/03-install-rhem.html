Guided exercise 3 rhem-install

Install Red Hat Edge Manager

Register the server with Red Hat, install the Edge Manager packages, tell it its name, and start it. Then look at what is actually running.

Outcomes

  • RHEM 1.4.0 running on rhem as 17 containers managed by systemd.
  • Its own certificate authority (CA), created on first start, in /etc/flightctl/pki.
  • You know which service does what, and where state lives.

Before you begin

On the workstation, in ~/edgelab, confirm that the earlier exercises are complete:

./lab start rhem-install

Instructions

Register the server with Red Hat

RHEL can only install packages from Red Hat's CDN after it is registered. You register with the organization ID and activation key that you saved in module 0. Display them on the workstation:

cat inputs/rhsm-activation

org=1234567
key=my-activation-key

Then, in the server VM, register with those two values. This is the one command in the lab where you enter values of your own: put your organization ID after --org and your activation key after --activationkey.

sudo subscription-manager register --org <organization_id> --activationkey <activation_key>

With the example values shown above, the command would be:

sudo subscription-manager register --org 1234567 --activationkey my-activation-key

The system has been registered with ID: …
The registered system name is: rhem.lab.internal

If you do not have an activation key, sudo subscription-manager register with no options asks for your Red Hat login and password instead.

Note

Why an activation key? It registers a machine without a person's username and password. That is the same method you would use to register hundreds of servers, or to build images in a pipeline.

Enable the Edge Manager repository

sudo subscription-manager repos --list | grep edge-manager-1.4

Repo ID:   edge-manager-1.4-for-rhel-9-x86_64-rpms
Repo ID:   edge-manager-1.4-for-rhel-9-x86_64-debug-rpms
Repo ID:   edge-manager-1.4-for-rhel-9-x86_64-source-rpms

These are the repositories your subscription offers for Edge Manager 1.4. If nothing is listed, the subscription does not include Edge Manager. Enable the first one, which holds the packages, and list what is in it:

sudo subscription-manager repos --enable edge-manager-1.4-for-rhel-9-x86_64-rpms

Note

The agent and the server should be the same version. This repository choice (1.4) is what you repeat when building device images.

Install the server and the CLI

sudo dnf -y install flightctl-services flightctl-cli
rpm -q flightctl-services flightctl-cli podman

flightctl-services-1.4.0-1.el9.x86_64
flightctl-cli-1.4.0-1.el9.x86_64
podman-5.8.5-3.el9_9.x86_64

This is small and quick: the package holds no server software itself. It installs quadlets, files that tell systemd to run a container as a service. Look at one:

ls /usr/share/containers/systemd/
cat /usr/share/containers/systemd/flightctl-db.container

In the database's file, find the Image= line (which container to run), the Volume=flightctl-db:… line (where its data is kept) and Restart=always.

Note

Why quadlets? Each service is an ordinary systemd unit: systemctl status, journalctl -u, restart on failure and start at boot all work as for any RHEL service, with no Kubernetes underneath. You use the same mechanism to run applications on the edge devices in module 9.

Let the server pull Red Hat's container images

The Edge Manager containers come from registry.redhat.io, which needs a login. Your pull secret is that login. Copy it from the workstation to the server VM:

scp -F ~/edgelab/ssh_config inputs/pull-secret.json rhem:pull-secret.json

In the server VM, install it as the registry login file for root's podman, and remove the copy:

sudo install -D -m 0600 pull-secret.json /root/.config/containers/auth.json
rm pull-secret.json

Test it by pulling a small image that needs the login:

sudo podman pull registry.redhat.io/ubi9/ubi-micro

Trying to pull registry.redhat.io/ubi9/ubi-micro:latest...
...output omitted...
Writing manifest to image destination

ubi-micro is Red Hat's smallest base image, about 24 MB. Which image you pull does not matter here; a successful pull from registry.redhat.io proves the login works. An "unauthorized" error means the file is missing or in the wrong place.

  • /root/.config/containers/auth.json is where podman, run as root, looks for registry logins. A pull secret is already in that file's format, so installing it is a copy.
  • install -D -m 0600 creates the folders on the way and makes the file readable by root only.
  • Edge Manager's services run as root, which is why the login belongs to root and not to cloud-user.

Important

The file location matters. Red Hat's guide uses sudo podman login registry.redhat.io, which stores the login under /run and loses it at reboot. /root/.config/containers/auth.json survives reboots. A wrong location shows up as every service stuck in auto-restart with "unable to retrieve auth token" in journalctl -u flightctl-db.

Tell Edge Manager its name

One setting is required: the base domain. Everything else in /etc/flightctl/service-config.yaml can stay at its default for now.

sudo vi /etc/flightctl/service-config.yaml

The fifth line of the file reads baseDomain: with nothing after it. Add the server's name, so that the line reads exactly as follows, with two spaces at the start and one space after the colon. Then save and quit.

  baseDomain: rhem.lab.internal

Confirm the change:

head -5 /etc/flightctl/service-config.yaml

global:
  # The base domain for the deployment, from which the service FQDNs are derived.
  # If provided, must be a fully qualified domain name (FQDN) like "example.com" or a hostname that resolves via DNS.
  # If not provided, defaults to the system's hostname FQDN ('hostname -f').
  baseDomain: rhem.lab.internal
SettingValueEffect
baseDomainrhem.lab.internalThe name in the server's certificates, in the login redirects, and in the enrollment configuration baked into device images. Changing it later means re-issuing certificates and rebuilding device images, so it is chosen first.
generateCertificatesbuiltin (default)On first start the server creates its own CA and signs its certificates with it. none is for bringing your own CA.
auth.typeoidc (default)Logins go through an OpenID Connect provider. The bundled one checks users against Linux accounts inside its own container (module 4).

Start it

sudo systemctl enable --now flightctl.target

The command returns in seconds, but the first start downloads about 7 GB of container images. Watch until nothing is left starting (two to five minutes; leave with Ctrl+C):

watch -n 5 'systemctl list-units "flightctl*" --no-pager'

It is ready when the ACTIVE and SUB columns of every line read one of these:

ACTIVE SUBSeen onMeaning
active runningMost .service linesA container that is up and stays up.
active exitedThe -init, -migrate, -wait and -network servicesA one-time setup job that finished successfully: create certificates, create database users, migrate the schema.
active activeflightctl.target, the last lineA target is a named group of units, not a process, so it has nothing to run or exit. active means the group has been started.

Note

While images download, services show activating auto-restart or failed. systemd keeps retrying every 30 seconds, so that clears by itself. If it does not, read sudo journalctl -u flightctl-db -n 30: the database is first in the chain.

Look at what is running

A plain sudo podman ps prints seven columns and is too wide to read comfortably. The --format option chooses the columns:

sudo podman ps --format "table {{.Names}} {{.Status}}"

NAMES                          STATUS
flightctl-cli-artifacts        Up 4 minutes
flightctl-kv                   Up 4 minutes
flightctl-db                   Up 4 minutes
...output omitted...
flightctl-ui                   Up 3 minutes
flightctl-gateway              Up 3 minutes
  • table prints a header row and lines the columns up.
  • Each {{.Name}} is one column. The ones used most are {{.Names}}, {{.Status}}, {{.Image}} and {{.Ports}}. The same option works with podman images and other listing commands.

One container publishes ports to the network. List them:

sudo podman port flightctl-gateway

8443/tcp -> 0.0.0.0:443
3443/tcp -> 0.0.0.0:3443
4317/tcp -> 0.0.0.0:4317
7443/tcp -> 0.0.0.0:7443
7444/tcp -> 0.0.0.0:7444
8445/tcp -> 0.0.0.0:8445

Each line reads "port inside the container -> port on the server". What each container is for:

ContainerJob
flightctl-dbPostgreSQL. All state: devices, fleets, specs, status, events.
flightctl-kvRedis. Work queues and caches between the services; nothing you would need to keep.
flightctl-apiThe API, for you (CLI, UI) and for agents.
flightctl-worker, -periodicBackground work: turn fleet templates into per-device specs, run rollouts, poll repositories.
flightctl-gatewayThe front door (nginx). The only container with ports open to the network.
flightctl-ui, -cli-artifactsThe web console, and downloads of the CLI.
flightctl-pam-issuerThe bundled login provider.
flightctl-remote-accessRemote console sessions to devices.
flightctl-imagebuilder-*, -delta-workerBuilding device images from the UI, and delta updates. Not used in this lab.
flightctl-alert*, -telemetry-gatewayAlerts and device metrics.

Two ports matter:

PortUsed byHow the caller proves who it is
443You: web UI, CLI, loginUsername and password, then a token
7443Agents on devicesA client certificate signed by this server's CA (mutual TLS)

Note

Effect on the edge. A device needs to reach exactly one name on one port, 7443, outbound. No inbound access to devices is ever needed, which is what makes them manageable behind NAT, firewalls and unreliable links.

Find the state: certificates and data

sudo ls -l /etc/flightctl/pki
openssl x509 -in /etc/flightctl/pki/ca.crt -noout -subject -dates
sudo openssl x509 -in /etc/flightctl/pki/flightctl-api/server.crt -noout -subject -dates -ext subjectAltName
sudo podman volume ls
WhatWhereWhy you care
CA certificate and private key/etc/flightctl/pki/ca.crt, ca.keySigns every device certificate. Whoever holds ca.key can create devices the server will trust. Valid 10 years.
Server certificate/etc/flightctl/pki/flightctl-api/server.crtLists the names agents may use: rhem.lab.internal and its api. and agent-api. forms. Valid 2 years.
Databasepodman volume flightctl-dbThe fleet's whole memory.
Configuration/etc/flightctl/service-config.yamlThe file you edited.

Note

Remember these three. CA, database and configuration together are this Edge Manager. They are what a backup has to contain. Losing the CA means re-enrolling every device.
